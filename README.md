# fomoxa-go

## 1. Overview

fomoxa-go is the Go runtime implementation of the Fomoxa protocol.
It implements framing, the schema handshake, heartbeat, and a non-blocking tick loop over TCP or UDP, as defined by the Fomoxa specification.
The module declares no third-party dependency; it has no `go.sum` entries and imports only the Go standard library.
It starts no goroutines and does not use the `context` package; every socket operation is driven by an explicit call to `Tick`.

## 2. Authoritative References

The behavior of this package is defined by the documents below, not by this file.
Where this package and any other Fomoxa SDK disagree on behavior, the referenced documents decide, and agreement between two SDKs is not by itself evidence of correctness.

| Document | Scope |
|---|---|
| [RFC-0001](https://github.com/fomoxa-protocol/protocol-specification) | What Fomoxa is, and the design decisions behind it |
| [RFC-0002](https://github.com/fomoxa-protocol/protocol-specification) | Wire format: primitives, string, bytes, model, array, enum, version differences |
| [RFC-0003](https://github.com/fomoxa-protocol/protocol-specification) | Conformance: the test vectors an implementation must pass |
| [Implementation guide](https://github.com/fomoxa-protocol/protocol-implementation-guide) | Framing, handshake, heartbeat, and the transport contract |

## 3. Architecture

The protocol is divided into three layers.
This package implements one of them.

```
application
     |
codec        RFC-0002 - Model <-> bytes                 generated by fomoxac,
                                                          not part of this repository
     |
runtime      implementation guide - frames,              frame.go, session.go,
(this repo)  handshake, heartbeat, tick loop, events      handshake.go, conn.go, server.go
     |
transport    TCP or UDP, or a caller-supplied Transport   transport.go, transports_unix.go
```

A message payload is opaque from the transport up to the event handed to the application.
No code in this repository reads or writes the content of a payload; encoding and decoding a Fomoxa model is `fomoxac`'s generated output, not something reimplemented here.

## 5. Quick Start

### 5.1 Client

```go
conn, err := fomoxa.DialTCP("127.0.0.1:7788", schema, fomoxa.DefaultConfig())
if err != nil {
    return err
}
defer conn.Close()

for now := range ticker.C {
    for _, event := range conn.Tick(now) {
        switch event.Kind {
        case fomoxa.EventReady:
            // Send is refused with ErrNotReady before this point.
        case fomoxa.EventMessage:
            handle(event.MessageID, event.Payload)
        case fomoxa.EventHandshakeFailed, fomoxa.EventDisconnected:
            return event.Err
        }
    }

    if conn.State() == fomoxa.StateReady {
        _ = conn.Send(messageID, payload)
    }
}
```

`ticker` is any `<-chan time.Time`, typically a `time.NewTicker`.
`Send` returns `ErrNotReady` until the session's `State()` becomes `StateReady`; no application byte reaches the transport before that point.

### 5.2 Server

```go
server, err := fomoxa.ListenTCP("127.0.0.1:7788", schema, fomoxa.DefaultConfig())
if err != nil {
    return err
}
defer server.Close()

for now := range ticker.C {
    for _, event := range server.Tick(now) {
        if event.Kind == fomoxa.EventMessage {
            _ = server.Send(event.Peer, replyID, event.Payload)
        }
    }
}
```

### 5.3 Examples

`examples/echo-server` and `examples/echo-client` are a complete, runnable client and server pair using `examples/echoschema` as their schema.

```sh
go run ./examples/echo-server -network udp
go run ./examples/echo-client -network udp
```

Both accept `-network tcp` or `-network udp` (default `tcp`); the server accepts `-listen`, the client `-connect` (default `127.0.0.1:7788` for both).
`examples/echoschema/schema.go` declares its two messages by hand, in the shape that `fomoxac`'s generated output takes.

## 6. Schema Construction

The runtime never computes a schema fingerprint; it only compares values supplied by the application.
For each message, the application supplies a `fomoxa.Message`: an ID, a fingerprint, and a prefix-fingerprint chain, where entry `k-1` of the chain is the fingerprint that covers the first `k` fields, and the last entry equals the message's own fingerprint.

```go
type Message struct {
    ID          uint32
    Fingerprint uint64
    Prefixes    []uint64
}
```

`fomoxac` generates this table for Go as `FomoxaMessages` in a generated `handshake.go`; mapping it into a `fomoxa.Schema` is mechanical:

```go
messages := make([]fomoxa.Message, 0, len(generated.FomoxaMessages))
for _, m := range generated.FomoxaMessages {
    messages = append(messages, fomoxa.Message{
        ID:          m.ID,
        Fingerprint: m.Fingerprint,
        Prefixes:    m.Prefixes,
    })
}
schema, err := fomoxa.NewSchema(generated.FomoxaSchemaFingerprint, messages)
```

`NewSchema(fingerprint uint64, messages []Message) (*Schema, error)` sorts the messages by ID and rejects three cases: a message ID declared twice, a message with more than `MaxFieldCount` (`0xFFFF`, 65535) fields, and a message whose last prefix entry does not equal its own `Fingerprint`.

The prefix chain is what makes RFC-0002 §9.1 answerable on the wire.
A single fingerprint per message cannot answer it, because hashing `Item{id, name}` and `Item{id, name, hp}` loses the prefix relation between them.
The chain commits to each prefix separately, so the two ends can compare at `k = min(their field count, ours)`, which is §9.1's requirement that the shorter type sequence be an exact prefix of the longer one.

Two peers whose schemas differ can still connect, as long as every message both ends declare agrees on the fields both ends carry.
Appending a field at the end of a message is not a conflict; RFC-0003 §8.6 vectors V-001 and V-002 require such a pair to interoperate, and `TestAppendingAFieldAtTheEndMustInteroperate` in `handshake_test.go` verifies both directions of that case.

## 7. Configuration

```go
type Config struct {
    HandshakeTimeout    time.Duration
    HeartbeatInterval   time.Duration
    HeartbeatTimeout    time.Duration
    MaxFramesPerTick    int
    ReadBufferSize      int
    MaxPeerBacklog      int
    MaxDatagramsPerTick int
}
```

| Field | Default | Meaning |
|---|---|---|
| `HandshakeTimeout` | 5s | Client: deadline for the whole handshake, query round included, measured from session start and never reset. Server: the silence window used to probe a peer that has not finished handshaking |
| `HeartbeatInterval` | 5s | How long silence lasts, once ready, before one probe is sent |
| `HeartbeatTimeout` | 15s | How long an unanswered probe is allowed before the peer is declared dead |
| `MaxFramesPerTick` | 64 | Frames processed from a single `Conn` per `Tick` call; on a TCP listener this budget also bounds new connections accepted per `Tick` |
| `ReadBufferSize` | 65536 (64 KiB) | Initial size of the per-connection receive buffer; it grows (capped at `MaxFrameLen`) if a frame does not fit |
| `MaxPeerBacklog` | 64 | Datagrams queued per UDP peer before the oldest queued datagram is dropped |
| `MaxDatagramsPerTick` | 512 | Datagrams a UDP listener reads from the socket per `Tick` call |

Any field left at its zero value (or a negative duration or count) is replaced by its `DefaultConfig()` value independently of the other fields, so a bare `Config{}` behaves identically to `DefaultConfig()`.
`NewConn` and `NewPeerConn` apply this normalization internally; `ListenTCP` and `ListenUDP` apply it before constructing the listener.
Worst-case dead-peer detection time on a ready session is `HeartbeatInterval + HeartbeatTimeout`, 20 seconds with the defaults.
The server has no absolute handshake deadline: a peer that keeps answering probes holds its slot indefinitely, which is specified behavior rather than something an implementation may tighten unilaterally.

## 8. Events

```go
type Event struct {
    Kind      EventKind
    Peer      PeerID
    MessageID uint32
    Payload   []byte
    Verdict   Verdict
    Err       error
}
```

| `EventKind` | Raised when |
|---|---|
| `EventConnected` | The first tick of a session, always, on every transport |
| `EventReady` | Verdict `Accept` arrived (client) or was sent (server peer) |
| `EventHandshakeFailed` | Verdict `Version`, `Conflict`, or `Malformed`; a malformed handshake payload; or the client's handshake deadline |
| `EventMessage` | A data frame arrived while the session was ready |
| `EventProbe` | A probe arrived while ready; the ack was already written to the outbound queue |
| `EventAck` | An ack arrived while ready |
| `EventDisconnected` | The transport reported closed or failed, or the peer stopped answering a probe |

`Event.Verdict` is meaningful only on `EventHandshakeFailed`; it is the verdict byte behind the failure, and there is no separate table to translate it further.
`Event.Err` is set on both terminal events, `EventHandshakeFailed` and `EventDisconnected`, and describes the failure in words.
A session produces exactly one terminal event, once; a transport failure that follows a refused handshake adds nothing further.
`Event.Payload` is a copy made when the frame is decoded and remains valid for as long as the application holds it; it is not a view into a buffer the runtime reuses on the next tick.

| `State` | Meaning |
|---|---|
| `StateHandshaking` | Initial state; the handshake has not completed |
| `StateReady` | The handshake accepted; `Send` is permitted |
| `StateClosed` | The session has terminated; no further events are produced |

## 9. Handshake Protocol

The handshake is carried in `FrameHandshake` frames, always the client's initiative.

1. On its first tick, the client sends a hello: protocol version (currently 2), its schema fingerprint, and one item per declared message (ID, field count, fingerprint).
2. The server (or a peer `Conn` constructed with `NewPeerConn`) reads the hello. If it is malformed or declares more than 1,000,000 messages, the server refuses with `VerdictMalformed`. If the protocol version does not match, it refuses with `VerdictVersion`.
3. If the hello's schema fingerprint equals the server's own, the server accepts immediately without inspecting individual messages.
4. Otherwise, each message the server also declares is checked: a message the server does not declare is skipped; equal fingerprints match; if the two field counts are equal but the fingerprints differ, it is a conflict; if the peer declares fewer fields, its fingerprint is compared against the server's own prefix entry at that field count; if the peer declares strictly more fields, the message is queued to ask about.
5. If nothing needs asking, the server writes `VerdictAccept` and both ends become `StateReady`. If something needs asking, the server writes one query payload (a handshake frame whose first byte is the sentinel value 4, followed by the queried message IDs and field counts) instead of a verdict.
6. The client answers a query exactly once, from its own prefix chain, at the field counts asked; a query about a message it did not declare, an out-of-range field count, or a second query are all rejected locally as malformed.
7. The server checks the reply's item count, order, and message IDs against what it asked, then compares each returned fingerprint against its own prefix table: a match accepts, a mismatch is a conflict, a structural mismatch is malformed.
8. A third handshake payload from the client, after a verdict or during a pending query mismatch, is rejected as malformed; only one query round is possible per session.

| `Verdict` | Value | Meaning |
|---|---|---|
| `VerdictAccept` | 0 | Handshake accepted |
| `VerdictVersion` | 1 | Protocol version mismatch |
| `VerdictConflict` | 2 | A field disagreement at an index both ends carry |
| `VerdictMalformed` | 3 | A structurally invalid handshake payload |

A refusal frame is written to the outbound queue and flushed before the transport's send side is closed, so the peer receives the verdict rather than only an abrupt close.

### 9.1 Handshake payload layouts

All multi-byte integers are little-endian.

| Payload | Header | Per-item |
|---|---|---|
| Hello | 16 bytes: version u32, schema fingerprint u64, item count u32 | 14 bytes: message ID u32, field count u16, fingerprint u64 |
| Query | 5 bytes: sentinel byte `0x04`, item count u32 | 6 bytes: message ID u32, field count u16 |
| Query reply | 4 bytes: item count u32 | 12 bytes: message ID u32, fingerprint u64 |
| Verdict | 1 byte: the `Verdict` value | — |

A hello or query declaring more than 1,000,000 items is rejected as malformed without being fully parsed.

## 10. Wire Format

Frames are fixed and identical across every Fomoxa implementation (implementation guide §2).
All multi-byte integers are little-endian.

| `FrameType` | Value | Layout | Size |
|---|---|---|---|
| `FrameData` | 0 | `[00]['C']['Y'][message id u32][length u32][payload]` | 11 + length |
| `FrameProbe` | 1 | `[01]` | 1 byte, no body |
| `FrameAck` | 2 | `[02]` | 1 byte, no body |
| `FrameHandshake` | 3 | `[03][length u32][payload]` | 5 + length |

A data frame's magic bytes are `0x43` (`'C'`) and `0x59` (`'Y'`) at offsets 1 and 2.
`MaxMessagePayload` is 16 MiB (16,777,216 bytes); `MaxHandshakePayload` is 1 MiB (1,048,576 bytes); a frame type byte outside `0..3` is a violation.

On a byte-stream transport, frames run back to back and any violation is fatal: the stream decoder is poisoned and returns the same error on every subsequent call, since there is no point in the stream where framing can be safely resumed (`TestStreamDecoderStaysPoisoned`).
On a packet transport, one packet holds exactly one frame; a violation costs only that packet, and the session continues (`TestPacketViolationOnlyDropsThatPacket`).
This asymmetry is deliberate and both halves are covered by tests.

## 11. Transports

TCP and UDP ship in this repository.
Any other transport — TLS, WebSocket, QUIC — is implemented outside this package against the `Transport` interface and handed to `NewConn` or `NewPeerConn`; adding one does not require a change here.

```go
type Transport interface {
    Kind() Kind
    Send(b []byte) Status
    Receive(buf []byte) (n int, need int, status Status)
    CloseSend()
    Close()
}
```

| `Status` | Value | Meaning |
|---|---|---|
| `StatusOK` | 0 | The operation completed |
| `StatusPending` | 1 | Cannot complete now; the caller retries later |
| `StatusClosed` | 2 | The peer closed the connection cleanly |
| `StatusError` | 3 | The transport failed |
| `StatusTooLarge` | 4 | This frame will never fit; it is not retried, and the session continues |
| `StatusTooSmall` | 5 | The supplied buffer is smaller than `need` bytes; the packet is retained, not discarded |

A transport optionally implements `ErrorReporter` (`LastError() error`) to report the underlying cause behind a `StatusError` or `StatusClosed`; both built-in transports implement it.

`Kind() Kind` declares `KindStream` or `KindPacket` once, at construction.
A stream transport returns whatever bytes are available, in any quantity, and the framing layer inside this package reassembles them with a `streamDecoder`.
A packet transport must return exactly one whole packet per `Receive` call, or `StatusPending`, never a partial one.

`NewConn` is for the side that sends the hello; `NewPeerConn` is for the side that judges it.
Both return the same `*Conn`, with the same `Tick`, `Send`, `Close`, and `Transport()`, so a package that adds a transport can offer its own `Dial`/`Listen` helpers without touching this one.

### 11.1 TCP and UDP specifics

Both built-in transports are implemented with `syscall.RawConn`, reading and writing through a callback that returns `true` on the first attempt, so neither call blocks waiting for socket readiness.
TCP is a `KindStream` transport with `TCP_NODELAY` set; a partial kernel write is retained in an internal backlog and retried on the next `Send` or `Receive` call.
UDP is a `KindPacket` transport; a single send is capped at 65,507 bytes of payload (`StatusTooLarge` above that), and an ICMP port-unreachable response (`ECONNREFUSED`) is treated as `StatusPending` rather than as an error.

`ListenUDP`'s listener demultiplexes incoming datagrams by source address into a `Transport` per peer.
It tracks at most 1,024 distinct source addresses at once; a datagram from a new address past that ceiling is dropped without disturbing any running session.
Each tracked peer holds at most `MaxPeerBacklog` queued datagrams; past that, the oldest queued datagram is dropped, not the newest, so recent data survives a burst.
`ListenTCP`'s listener accepts up to `MaxFramesPerTick` new connections per `Tick` call, reusing that field as its per-tick accept budget.

## 12. Errors

| Error | Message |
|---|---|
| `ErrNotReady` | `fomoxa: session is not ready` |
| `ErrCongested` | `fomoxa: outbound frame is still in flight` |
| `ErrPayloadTooLarge` | `fomoxa: payload exceeds the 16 MiB message limit` |
| `ErrTransportLimit` | `fomoxa: frame exceeds what the transport can carry` |
| `ErrSessionClosed` | `fomoxa: session is closed` |
| `ErrUnknownPeer` | `fomoxa: no such peer` |
| `ErrUnsupported` | `fomoxa: non-blocking sockets are not implemented on this platform` |

`Send` refuses with `ErrCongested` if a frame is already queued and waiting for the transport to accept it, rather than queuing a second one; while a frame is queued, no other frame may pass it on that `Conn`.
A `Conn`'s outbound queue is bounded at 64 KiB across the data frame plus whatever control frames the protocol can owe at once; exceeding that ceiling ends the session, since it means the peer has stopped reading.

## 13. Platform Support

The TCP and UDP transports (`transports_unix.go`, `rawops_unix.go`) are built only for platforms matching the `unix` build tag.
On other platforms, `DialTCP`, `DialUDP`, `ListenTCP`, and `ListenUDP` return `ErrUnsupported` (`transports_other.go`).
Everything else in the package — framing, the handshake, the session state machine, `Conn`, `Server`, and any caller-supplied `Transport` — is portable across all platforms Go supports.

## 14. Design Invariants

| Property | Behavior |
|---|---|
| Non-blocking | Every method reports the state at the moment it is called and returns; no call in this package waits for I/O readiness. |
| No goroutines | The package starts no goroutines; the caller's loop drives all I/O and timing through `Tick`. |
| Time is a parameter | `Tick(now)` takes the instant explicitly; nothing in the package reads a clock on its own, so a full heartbeat expiry cycle can run in a test in microseconds (`TestDeathIsDetectedWithoutWaiting`). |
| The handshake gates the application | `Send` before `EventReady` returns `ErrNotReady`; no application byte reaches the wire before both ends agree on the schema. |
| Exactly one terminal event | A session produces `EventHandshakeFailed` or `EventDisconnected`, once, never both. |
| Probe on silence | A probe is sent only after the silence window closes, once per cycle; any valid frame (data, probe, ack, or handshake) resets the window, so a busy connection produces no heartbeat frames. |

## 15. Tests

```sh
go test ./...
go test -race ./...
```

The suite contains 75 top-level test functions across six files (91 including table-driven sub-tests), organized by the implementation guide's §11 checklist:

- **`frame_test.go`** — byte-exact frame layouts, a stream decoded one byte at a time, a stream decoder that stays poisoned after a violation, payload size ceilings, and that an oversized declared length is rejected without allocating a buffer of that size.
- **`handshake_test.go`** — all branches of the server's fingerprint comparison, the query round in both directions, malformed hello and query-reply payloads, protocol version mismatches, and the field-appended-at-the-end interoperability requirement from RFC-0003 §8.6.
- **`heartbeat_test.go`** — traffic suppressing probes, exactly one probe per silence window, any frame ending a probe cycle, a full expiry cycle driven by a fake clock, and the server's wider silence window while a peer is still handshaking.
- **`flow_test.go`** — a blocked transport holding and later resending exactly one frame, congestion refused rather than queued, an oversized frame not ending the session, the per-tick frame budget, byte-stream versus packet violation handling, and the outbound-queue ceiling under a peer that keeps probing without reading.
- **`interop_test.go`** — client and server driven against each other over an in-memory pipe on both `Kind` values, a schema conflict refusing both ends, a `Server` running multiple peers, and a `Conn` built with `NewPeerConn` against a hand-supplied transport.
- **`sockets_unix_test.go`** (`unix` build tag) — live TCP and UDP loopback sessions in both directions, a schema conflict over a real socket, a server-initiated disconnect, and two UDP clients kept isolated from each other on one listening socket.

CI (`.github/workflows/ci.yml`) runs on push to `main` and on pull requests: `gofmt -l .` must report no files, `go vet ./...`, `go build ./...`, and `go test -race ./...`, on `ubuntu-latest` with Go 1.22.
